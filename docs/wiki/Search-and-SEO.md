# Search visibility and SEO

[Wiki home](https://github.com/BitsofBitsofBitsofBits/shortbits.net/wiki) | [Source repository](https://github.com/BitsofBitsofBitsofBits/shortbits.net)

The site targets searches for **Caleb K Masters**, **BitsofBitsofBits**, and
the actual topics covered by its public content: IT support, systems
administration, automation, home lab infrastructure, and web development.
Technical SEO helps crawlers discover and understand that content; it does not
guarantee a particular ranking or an immediate traffic increase.

## What is implemented

- Descriptive, page-specific titles and descriptions, with visible links from
  the chooser and Online profile to the projects and technical blog.
- A consistent `https://www.shortbits.net` canonical host. The deployment's
  Caddy updater adds an HTTP **308** redirect from `shortbits.net`, retaining
  the path and query string. It never redirects the canonical host to itself.
  Caddy must explicitly declare `www.shortbits.net`; unsupported configurations
  fail rather than redirecting to an unconfigured site.
- Static HTML social metadata, page/collection entities, and breadcrumb
  structured data generated by `scripts/build-seo.mjs`. No extra client-side
  JavaScript or bot-specific content is used. Existing profile and article
  schema is preserved and connected to a consistent person identifier.
- Static blog articles and archive links, an RSS feed, and a sitemap containing
  public canonical pages and published articles. Article modification dates
  come from saved content timestamps, not the deployment clock.
- `max-image-preview:large` on indexable built pages. Google and Bing may
  choose their own titles, snippets, and result appearance.
- The legacy JavaScript blog reader remains usable for live/old links but is
  `noindex, follow`; search results should use deployed static article URLs.
  Admin, error, and other noindex helper pages are not added to the sitemap.
- `scripts/validate-site.mjs` checks sitemap URLs, missing/noindex pages,
  unique titles, descriptions, canonical URLs, static headings, and valid
  JSON-LD. Production checks also verify the generated social metadata.

Browser preferences and local storage are origin-specific. Someone moving
from the bare domain to `www` may need to reselect local preferences or sign
in again; this does not change server-side account/content data.

## Owner setup after deployment

1. Add **shortbits.net** as a Domain property in
   [Google Search Console](https://search.google.com/search-console/) and
   complete DNS ownership verification. Never commit account credentials or
   private verification material into the site.
   Alternatively, create a **URL-prefix property** for
   `https://www.shortbits.net/` and use HTML-file verification. Store the complete
   downloaded file contents in the **production** environment's GitHub Actions
   secret named `GOOGLE_SITE_VERIFICATION`. Deployment injects the file into
   the built site after building, before validation and upload. Missing or
   malformed contents stop deployment. The file stays out of the current
   repository tree and sitemap; root-level `google*.html` files are ignored.
   The verification URL (`https://www.shortbits.net/google<token>.html`) must
   remain publicly accessible for Google, so this is not a way to hide it
   from website visitors. After deployment, select **Verify** in Search Console.
   Keep the secret configured so Google can recheck ownership after future deployments.
   HTML-file verification does not verify a Domain property; that requires DNS.
2. Submit `https://www.shortbits.net/sitemap.xml`. Use URL Inspection on the
   homepage, professional profile, and a published article; check the
   rendered HTML and Google's selected canonical URL. Request indexing for
   important updated pages, rather than repeatedly submitting everything.
3. Add the site in [Bing Webmaster Tools](https://www.bing.com/webmasters/).
   Import the verified Search Console property if offered, or use Bing's
   ownership-verification process. Submit the same canonical sitemap.
4. Check that `https://shortbits.net/projects/?example=1` redirects once to
   `https://www.shortbits.net/projects/?example=1`, while the destination
   returns 200 and an unknown URL still returns a real 404.
5. Validate a profile/article with Google's
   [Rich Results Test](https://search.google.com/test/rich-results) and inspect
   indexing/crawl reports in both consoles after deployment.

Verification and sitemap submission are owner-account actions, not performed
automatically by the repository. No verification tokens have been invented.
Bing's optional [IndexNow](https://www.indexnow.org/documentation) submission
can be added later with an owner-configured verification key; it is not
enabled by this change.

## Improving results over time

Publish useful, original technical material: the problem, actual setup,
steps, trade-offs, troubleshooting, and measured outcomes when available.
Keep public professional information accurate, link relevant posts and
projects to each other, and link this site from the real GitHub/LinkedIn
profiles. Do not invent experience, reviews, benchmarks, or backlinks.

New blog posts are fully crawlable after deployment generates their HTML
and sitemap entries. Editing or unpublishing content also requires a rebuild
to update/remove the deployed copy.

Use Search Console and Bing Webmaster Tools to compare impressions, clicks,
queries, and indexed pages over several weeks. A `site:` search is a rough
spot check, not an authoritative indexing count. Search engines can take
days or weeks to recrawl changes, and longer to change rankings.

## Validation

```sh
node --test scripts/seo.test.mjs scripts/build-content.test.mjs scripts/build-site.test.mjs scripts/update-caddy-csp.test.mjs
node scripts/build-site.mjs --input scripts/fixtures/blog-posts.json
node scripts/validate-site.mjs --root .site-build
node scripts/browser-smoke.mjs --root .site-build
```

The production build runs SEO enrichment after content/resume generation,
before CSS optimization, versioning, and compression. Source HTML keeps its
hand-authored metadata; production supplies the complete, normalized head.
The normal deployment still validates the candidate Caddy configuration
before applying it and rolls back a failed reload.
